# 012 — Home Assistant object storage

**Status**: Draft · **Kind**: New storage provider  
**Depends on**: 010 immediate Google-only refactor  
**Coordinates with**: 005, 008

## Summary

Add Home Assistant as an optional remote object store for encrypted `.kdbx`
databases. KeyVault gains a second `CloudStorageProvider` implementation while a
companion Home Assistant custom integration owns authenticated binary endpoints
and durable local storage on the Home Assistant host.

Home Assistant has no generic object-storage API. Its documented REST API is
JSON-oriented and does not provide arbitrary durable file CRUD. This feature
therefore does not upload vault bytes into entity state, events, media, backup API
records, or Home Assistant's internal `.storage` JSON files. Normal host backups
may include the companion's encrypted object directory. It ships an explicit
`keyvault_storage` custom integration with a narrow API for whole encrypted KDBX
objects.

The provider is self-hosted storage, not cloud sync by another name. KeyVault
continues to own sync policy, conflict handling, KDBX validation, local backups,
and local safe writes. Home Assistant stores opaque encrypted bytes and never
receives the master password or key file.

## Product behavior

1. Google Drive remains available and unchanged.
2. A user may configure one Home Assistant instance and select **Home Assistant**
   when linking an unlinked database.
3. Setup requires installing and enabling the companion custom integration on
   that Home Assistant instance, then pairing KeyVault with a short-lived,
   one-use code generated by a Home Assistant administrator.
4. KeyVault lists, creates, downloads, and replaces `.kdbx` objects exposed by the
   integration. One database mapping still names exactly one provider and one
   remote object.
5. Existing Google mappings remain Google mappings. No mapping is switched or
   migrated automatically.
6. Unlinking removes only the local mapping. It does not delete the Home Assistant
   object, matching current remote-file behavior.
7. The UI explains before pairing that Home Assistant receives only the encrypted
   `.kdbx`. Pairing returns a random credential scoped only to the companion's
   object API; KeyVault never receives a Home Assistant user access/refresh token.
8. An unavailable or restarting Home Assistant instance produces a safe sync
   error and leaves local and remote bytes untouched.

## Goals

1. Implement a real second adapter using spec 010's provider-neutral port and
   remote identity rules.
2. Store every mapped remote as one complete, directly downloadable `.kdbx`.
3. Preserve spec 008's mutex, backup, write-verify-converge, and ambiguous-write
   recovery invariants.
4. Use a companion-scoped bearer credential established through one-use pairing;
   never collect a broad Home Assistant user token.
5. Make server writes atomic and bounded; interrupted writes expose either the
   previous complete object or the new complete object, never partial bytes.
6. Keep Home Assistant implementation independent from KDBX secrets and semantic
   parsing.
7. Add only infrastructure required by two real providers: one minimal resolver
   and one provider choice in the existing sync flow.

## Non-goals

- Using Home Assistant's core REST endpoints as an object store without the
  companion integration.
- Storing bytes in states, attributes, events, recorder, media source, backup
  records, or `.storage` JSON. Normal Home Assistant host backups intentionally
  include the companion's data directory for disaster recovery; the backup API is
  never used as an object operation or provider version history.
- Decrypting, indexing, validating passwords, or rendering KDBX contents on the
  Home Assistant host.
- Multiple Home Assistant instances in one KeyVault installation.
- Automatic Google-to-Home-Assistant migration or provider switching.
- Remote delete, rename, folders, sharing, browser editing, or public download
  links.
- Home Assistant automations, entities, sensors, services, or change events for
  vault activity. These would create unnecessary metadata exposure.
- Home Assistant add-on, Samba, WebDAV, MQTT, or network-share transports.
- Home Assistant Cloud/Nabu Casa dependency. A user may expose their instance by
  any supported HTTPS route, but KeyVault does not require or configure one.
- Flutter web support in the first delivery. Android, iOS, macOS, Windows, and
  Linux are required.
- HACS publication or inclusion in Home Assistant Core. Initial distribution is
  a versioned companion-integration archive with manual custom-component install.

## Architecture

```text
existing sync UI/BLoCs
    -> existing coordinators and use cases
        -> DatabaseSyncRepository
            -> DatabaseSyncOrchestrator
                -> CloudStorageProviderResolver
                    -> GoogleDriveStorageProvider
                    -> HomeAssistantStorageProvider
                        -> HomeAssistantPairingService
                        -> HomeAssistantStorageApiDataSource
                            -> HTTPS
                                -> keyvault_storage custom integration
                                    -> atomic object-file store
```

### Application rules

1. Spec 010's immediate slice lands first. This spec consumes its
   `CloudStorageProvider`, provider-neutral models, safe errors, mapping schema,
   and `(providerId, remoteFileId)` identity.
2. `DatabaseSyncRepository` remains the application-facing boundary.
   Presentation never receives provider adapters, HTTP responses, OAuth tokens,
   or Home Assistant SDK types.
3. `HomeAssistantStorageProvider` is a data adapter under
   `features/password_manager/data`. It composes provider-specific auth and HTTP
   data sources and maps all output to spec 010 domain models.
4. A minimal `CloudStorageProviderResolver` becomes justified only because two
   production providers exist. It resolves an exact persisted `providerId`; no
   plugin discovery, reflection, dynamic loading, service locator access, or
   fallback provider is allowed.
5. Resolution failure remains spec 010's `unsupportedProvider` and performs no
   auth, remote I/O, local write, backup, or mapping mutation.
6. Existing coordinators own connect, provider choice, list, link, and disconnect
   sequencing. BLoCs remain event/state translation only.
7. Home Assistant companion code lives under
   `home_assistant/custom_components/keyvault_storage/`. This is a deployable
   companion artifact, not a new Flutter feature.

### Stable identity

The provider ID is the permanent machine value:

```text
home_assistant
```

It never contains a URL, host, port, Home Assistant user, installation name, or
version.

The custom integration creates one random installation UUID at first setup and
persists it in its config entry. Every returned `remoteFileId` is an opaque,
URL-safe value binding that installation UUID to a random object UUID. Only the
Home Assistant adapter/server may decode it. Application, mapping, picker, and
sync code treat it as an indivisible string.

This prevents a mapping created against Home Assistant instance A from being
silently executed against instance B after the configured base URL changes. An
instance mismatch returns `notFound` and performs no write. Remote display names
never participate in identity.

## Home Assistant companion integration

### Installation and lifecycle

- Domain: `keyvault_storage`.
- Minimum package: `manifest.json`, `__init__.py`, `config_flow.py`, `http.py`,
  `store.py`, translations, and tests.
- Setup uses a config entry; no `configuration.yaml` secrets are required.
- Exactly one config entry is allowed per Home Assistant instance.
- Integration-level setup registers HTTP views exactly once. Config-entry setup
  creates a private storage directory, verifies it is writable, and only then
  publishes an active runtime store to those views. A missing, failed, unloaded,
  or reloading entry makes every view return a fixed `503` without touching disk.
- Unloading removes runtime state and closes open resources; routes remain
  registered but fail closed until successful reload. Repeated setup/unload/reload
  must not duplicate routes or retain an old store. Stored objects remain.
- Removing the config entry does not delete vault objects without a separate,
  explicit destructive confirmation in Home Assistant. Destructive removal is
  outside KeyVault's API.

### Storage layout

Committed objects live under a dedicated directory owned by the integration,
outside Home Assistant's `.storage` JSON namespace. Exact absolute paths are an
implementation detail and must never be returned by the API or logged.

Each committed object is one regular file. Its physical filename contains only a
random object UUID and a bounded URL-safe encoding of the display name. There is
no per-object metadata, lock, checksum, or journal sidecar. Display metadata is
derived from filename, file stat, and committed bytes.

Required filesystem behavior:

1. Create a same-directory exclusive temporary file with mode `0600` where the
   platform supports POSIX modes.
2. Stream request bytes into it while enforcing the size limit and computing the
   response checksum.
3. Flush and fsync the file.
4. Atomically install with no-overwrite semantics for create, or `os.replace` for
   replacement.
5. Fsync the parent directory where supported.
6. Return metadata only after reopening or restating the committed target.
7. On cancellation or failure, remove the temporary file and preserve the old
   target. Startup removes stale temporary files before views become available.
8. Serialize writes per object. List/read may run concurrently with a write only
   when they continue to observe the old committed file until atomic replace.
9. A store-wide catalog lock serializes create identity allocation and quota
   checks. Two concurrent creates cannot reuse identity or both pass the 1,000th
   object boundary. Equal display names are allowed and remain distinct by ID.

Internal temporary files are never listed or addressable through the API. A
process kill at every write phase must leave the API exposing exactly one old or
new complete KDBX object at the mapped identity.

### Limits and validation

- Maximum object size: 64 MiB in the initial protocol. App and server enforce the
  same bound because spec 010's current port holds whole byte arrays; raising it
  requires measured client-memory evidence or an end-to-end streaming contract.
- Maximum display-name UTF-8 length: 180 bytes before physical encoding.
- Maximum committed objects: 1,000 per integration instance.
- Accepted display names are one non-empty basename ending in `.kdbx`, with no
  path separators, control characters, `.`/`..`, or normalization ambiguity.
- Object IDs must pass strict canonical decoding and installation-ID validation
  before any filesystem lookup.
- Request bodies are streamed and counted. Missing or dishonest
  `Content-Length` never bypasses the limit.
- Symlinks, hard links, directories, device files, and paths escaping the storage
  root are rejected.
- The integration stores opaque bytes and does not parse or decrypt KDBX. Client
  and end-to-end tests prove uploaded objects remain KeePass-openable.

## Authentication and transport

Home Assistant's authorization-code flow currently has no documented PKCE
contract and issues user tokens with permissions broader than this storage API.
This provider therefore does not request or store a Home Assistant user token.

1. A Home Assistant administrator opens the integration's local options flow and
   generates a cryptographically random 256-bit pairing code. Only a SHA-256 hash,
   creation time, expiry, and random slot ID are persisted; plaintext is displayed
   exactly once.
2. A pairing code expires after five minutes, is single-use, and is invalidated
   when a new code is generated for the same slot. At most 20 active client slots
   and one pending code per slot exist.
3. User enters normalized Home Assistant base URL and pairing code in KeyVault.
   `POST /pair` sends it as `Authorization: Pairing <base64url-code>` and exchanges
   it for a separate random 256-bit storage token bound to that slot and
   installation. Server atomically consumes the code before issuing the token and
   persists only the storage-token hash.
4. Storage token grants only the fixed `keyvault_storage` routes. It is not a Home
   Assistant access token and cannot call entities, services, events, WebSocket,
   config, backup, or any other Home Assistant API.
5. Every protected view uses `requires_auth = false` and performs the same custom
   authentication guard before parsing identity/name/body or touching storage.
   It accepts the storage token only in `Authorization: Bearer`; query-string
   tokens, cookies, signed paths, and Home Assistant user tokens are rejected.
6. Token hashes are compared in constant time. Pairing attempts are bounded by a
   store-wide rate limiter and fixed failure delay, with no distinction between
   unknown, expired, consumed, or wrong code. Limits survive restart sufficiently
   to prevent restart-based brute-force reset: pending-code record persists attempt
   count and next-allowed UTC instant atomically with its hash.
7. App stores plaintext storage token only in existing platform secure storage.
   Server returns it once. It never enters mapping JSON, state,
   `Equatable.props`, `toString`, clipboard, crash reports, or logs. Home Assistant
   backups may contain verifier hashes but never plaintext tokens; restore follows
   the mandatory credential-reset boundary below before any route becomes active.
8. Disconnect calls authenticated `POST /unpair`, which atomically removes that
   token hash and confirms only that the presented slot can no longer authenticate;
   app then erases local token. On no-response/transport failure, app erases the
   local token and instructs the user to revoke its slot in Home Assistant.
9. Home Assistant options list slots by random short label and creation time only,
   never token/hash or device/account metadata. Administrator may revoke any slot;
   revocation takes effect before the options flow reports success.
10. All production base URLs use HTTPS with normal platform certificate and
    hostname validation. No trust-all callback, certificate pin bypass, or
    persisted exception exists. Plain HTTP is permitted only for automated
    loopback tests, never user configuration.
11. Redirects may not change origin. Pairing/storage credentials are sent only to
    the normalized origin entered and confirmed by the user.
12. Integration removal invalidates all in-memory guards. Reinstalling against
    retained objects creates a new installation identity and requires fresh
    pairing; old mappings cannot silently bind to it.
13. Restoring a Home Assistant backup is a credential-reset boundary. Before
    publishing runtime store, companion must detect restore through a supported
    platform lifecycle signal, atomically delete every pending pairing code and
    storage-token slot, and persist completion. Objects and installation identity
    remain, so mappings resume only after fresh pairing. Until reset completes,
    every route including `/pair` returns fixed `503`; no token from before or from
    inside restored backup may authenticate even transiently. A server/runtime
    without reliable restore detection is unsupported and keeps provider disabled.

## Binary API v1

All routes are custom integration views under:

```text
/api/keyvault_storage/v1
```

The documented Home Assistant core REST API remains untouched. JSON responses
use `application/json`; object bodies use `application/octet-stream`.
`POST /pair` is the sole route authenticated by a pending pairing code; every
other route requires an active storage token.

| Method and route | Semantics |
| --- | --- |
| `GET /info` | Protocol version, installation-bound identity, maximum object bytes, and empty optional-capability set |
| `POST /pair` | Exchange one unexpired one-use pairing code for one storage token; no object access |
| `POST /unpair` | Revoke presented storage-token slot before confirming success |
| `POST /objects/list` | JSON body with bounded optional query; immutable metadata snapshot of eligible committed `.kdbx` objects |
| `POST /objects/metadata` | JSON body with opaque ID; fresh metadata for one committed object |
| `POST /objects/create` | Raw body plus bounded name header; server generates a new identity and never targets an existing object; equal names remain distinct |
| `POST /objects/read` | Opaque ID header; stream exact committed bytes |
| `POST /objects/replace` | Opaque ID header plus raw body; atomically replace exact object bytes |

No `DELETE`, rename, path, history, Home Assistant user-auth, or generic
filesystem endpoint exists.

Metadata JSON contains only:

```json
{
  "id": "opaque-installation-bound-id",
  "name": "vault.kdbx",
  "size": 1234,
  "modifiedTime": "ISO-8601 UTC",
  "contentChecksum": "lowercase-md5"
}
```

MD5 is retained only for compatibility with the existing sync baseline and is
not used as a security primitive. Create/replace and single-object metadata
responses return a checksum computed from committed bytes. List may return
`contentChecksum: null` to avoid hashing every vault; spec 010's existing
download-and-hash fallback remains mandatory.

Failure responses and diagnostics use fixed machine codes and fixed safe messages.
They never include an exception, traceback, absolute path, Home Assistant user
ID, token, request body, object bytes, remote ID, display name, or host. Successful
metadata responses and spec 010 mappings contain their required opaque ID and
display name; those fields remain forbidden from KeyVault, companion-integration,
and validated default Home Assistant logs, errors, analytics, and test evidence.
Fixed endpoint URLs contain no identity or display name. The integration never
logs request headers/bodies, and supported-server validation proves default Home
Assistant access logs do not record those values; custom reverse-proxy header
logging is outside control and called out in setup guidance.
Client mapping is:

| HTTP/protocol condition | `CloudStorageErrorCode` |
| --- | --- |
| User cancels pairing | `cancelled` |
| Pairing code rejected | `authenticationFailed` |
| Storage token missing, revoked, or invalid | `authorizationRequired` |
| Authenticated slot denied by server policy | `forbidden` |
| Object or installation identity absent/mismatched | `notFound` |
| Atomic create collision or explicit stale protocol response | `conflict` |
| `413` or advertised client-side size rejection | `malformedResponse` |
| Client/request timeout | `timeout` |
| DNS, TLS connection, socket, or no-response failure | `networkUnavailable` |
| Invalid JSON, fields, checksum, ID, or protocol version | `malformedResponse` |
| `429` | `rateLimited` |
| `500..599` | `serverFailure` |
| Every other unmapped condition | `unknown` |

Storage tokens do not refresh. An authorization failure requires fresh pairing and
is never replayed automatically. Create/replace retry is allowed only when the
client can determine no request body bytes were dispatched. A failure after
dispatch is ambiguous and enters spec 008 recovery; it is never blindly replayed.

## Provider capabilities and safety category

Initial declared optional capability set is empty:

```text
conditionalWrite: absent
versionHistory: absent
atomicCreateIfAbsent: absent
changeNotification: absent
```

Atomic local replacement on the Home Assistant host protects object integrity;
it does not prove server-enforced conditional write between clients. Create always
allocates a new random object identity, so it does not implement create-if-absent
for a shared logical target; equal names are valid separate objects. The provider
therefore starts in spec 010's **Ricostruibile** category and must use spec 008's
full read, write, read-back, and convergence flow.

Before this adapter may ship, spec 010 evidence must exist under:

```text
specs/010-multi-cloud-storage/evidence/home_assistant/
```

Required live-service subjects are `base_operations` and `single_file`, both
`present`, with sanitized counter-probes. Optional capabilities remain absent
unless separate real-service evidence proves them and code exposes immutable
`VerifiedCapability` values. Unit tests, source inspection, or confidence in
`os.replace` cannot upgrade a capability.

The single-file interruption probe kills Home Assistant during create and replace
at each injectable phase, restarts it, downloads the mapped object, and opens it
with a KeePass-compatible implementation. Every phase must expose either old or
new complete content and no partial/duplicate logical object.

A separate live contention probe drives two clients through synchronized
replace/read-back interleavings, including disconnect after body dispatch and
Home Assistant restart. It must demonstrate honest ambiguous outcomes, retained
local state, no partial remote bytes, and eventual spec 008 convergence. Fake
provider/model tests do not substitute for this adapter/server probe.

## Mapping and configuration

- Existing spec 010 mapping schema remains unchanged. Home Assistant mappings use
  `providerId: home_assistant` and the opaque installation-bound
  `remoteFileId`.
- Base URL, storage token, pairing metadata, and installation identity are
  provider configuration, not database mapping fields.
- Provider configuration is global and supports one Home Assistant instance.
- Changing the base URL disconnects first and does not rewrite mappings. Existing
  Home Assistant mappings stay visible but disabled until the new origin is
  freshly paired and proves the same installation identity. A different instance
  never inherits them.
- Removing provider configuration never deletes mappings or remote objects.
- Mapping and provider configuration writes never touch `.kdbx` bytes.

## Functional requirements

### FR-1 — Companion object store

Versioned custom integration exposes only authenticated list, metadata, create,
download, and replace operations over bounded complete `.kdbx` objects.

### FR-2 — Atomic committed object

Create and replace follow the required temp, flush, fsync, atomic-install, and
post-install verification sequence. Failure preserves the prior committed object
and never exposes partial target bytes.

### FR-3 — Home Assistant provider adapter

Adapter implements spec 010's port with stable ID `home_assistant`, exact safe
error mapping, installation-bound opaque IDs, checksum-null fallback, and no
KDBX parsing. Account summary uses fixed label `Home Assistant` with no email or
Home Assistant user identity.

### FR-4 — Scoped pairing

Five native platforms complete one-use pairing, secure storage-token persistence,
slot revocation, and reconnect. No Home Assistant user access/refresh token or
long-lived access-token input is added.

### FR-5 — Two-provider resolution

Minimal resolver selects Google Drive or Home Assistant by exact mapping/provider
choice. No fallback, guessed provider, registry framework, or provider SDK type
crosses into presentation.

### FR-6 — Provider choice

Existing sync setup adds one accessible provider choice before connection. Once a
database is linked, its provider is read-only. Switching requires unlinking first
and explicitly linking another remote; no bytes are deleted or migrated.

### FR-7 — Sync safety parity

Manual sync, auto-sync, conflicts, mapping move/remove, timeout, local mutex,
backup, atomic local writer, ambiguous recovery, and write verification retain
specs 008 and 010 semantics.

### FR-8 — Safe metadata and diagnostics

Tokens, origins, paths, Home Assistant user/installation IDs, bytes, raw failure
responses, and exceptions never enter logs controlled by KeyVault, the companion
integration, or validated default Home Assistant configuration; nor UI errors,
mappings, analytics, or test artifacts. Required opaque remote ID and display name
enter only successful provider models and spec 010 mappings; they never enter
controlled diagnostics, errors, analytics, or evidence. Setup warns that a custom
reverse proxy configured to log authorization/identity headers can violate this
boundary. UI shows fixed provider-neutral safe errors only.

## Acceptance criteria

1. Home Assistant custom integration installs through a versioned archive on a
   supported Home Assistant release and refuses setup when storage is unwritable.
2. API contract tests prove every route, unpaired/wrong/expired/consumed/revoked-
   token failure, rate limit, bound, path attack, object type rejection,
   protocol-version failure, and fixed error response.
3. Create/replace fault injection at every write phase leaves old or full new
   bytes, never missing/truncated target; stale temps are removed after restart.
4. Symlink, hard-link, traversal, malformed ID, oversized body, dishonest length,
   invalid name, and 1,001st-object attempts fail before committed mutation;
   synchronized concurrent creates cannot cross quota or reuse identity.
5. Provider contract tests cover pair, disconnect/revoke, account summary,
   list/query, metadata, create, replace, download, checksum-null fallback, and
   every safe error row.
6. Pairing tests prove 256-bit generation, hash-only persistence, five-minute
   expiry, atomic one-use consumption, constant-time token comparison, restart-
   resistant rate limit, 20-slot limit, exact origin matching, secure-token
   persistence boundary, local admin revocation, and no request replay after body
   dispatch.
7. Same object UUID from two Home Assistant installations cannot execute the
   wrong mapping. Different installation returns safe `notFound` with zero write.
8. Resolver tests prove exact Google/Home Assistant selection and fail-closed
   unknown-provider behavior with no provider calls or local/remote mutation.
9. Existing Google provider characterization and five-platform smoke remain
   green and behaviorally unchanged.
10. Existing Home Assistant mapping survives base-URL change and can resume only
    after fresh pairing against the same installation identity.
11. Required spec 010 `base_operations` and `single_file` live evidence exists,
    is sanitized, and passes structural validation. No optional capability is
    declared present.
12. Spec 008 convergence, writer routing, backup, mutex, ambiguous recovery, and
    conflict suites pass with Home Assistant fakes, plus the live two-client
    contention/ambiguous-recovery probe.
13. Android, iOS, macOS, Windows, and Linux each pass setup, pair, create,
    restart, list, download, local-only sync, remote-only sync, conflict, auto-sync,
    revoke/reconnect, and KeePass-openability smoke. One platform never qualifies
    another.
14. Home Assistant OS and Home Assistant Container each pass install, restart,
   interrupted-write, backup/restore, and storage-permission smoke against the
   latest stable release at implementation freeze and its immediately previous
    monthly stable release. Artifacts record exact versions; oldest/latest cannot
    be inferred from one another.
15. `flutter analyze`, full `flutter test`, companion Python lint/type checks, and
    companion Python tests pass.
16. Android and iOS near-limit tests sync a generated 64 MiB object while
    recording peak RSS and process survival. If either supported device class
    cannot complete safely, release lowers the fixed app/server limit; it never
    waives the test or silently uploads a larger object.
17. Restore tests create active and revoked slots, capture backup, mutate slot
    state, restore, and prove every pre-backup and post-backup token receives `503`
    during reset then `401` after activation. Objects and installation identity
    survive; fresh pairing restores mapped sync. No supported server/runtime may
    infer this behavior without executing its restore lifecycle.

## Rollout and backout

1. Complete spec 010 immediate refactor and stabilize its Google behavior.
2. Build companion integration and protocol tests without app wiring.
3. Produce sanitized live `base_operations` and `single_file` evidence.
4. Add Home Assistant pairing/data sources and provider contract tests.
5. Add minimal resolver, DI, and provider-choice UI.
6. Run sync safety and Google regression gates.
7. Run five client-platform and two server-runtime matrices.
8. Publish companion archive and app support together; either side alone reports
   unsupported protocol and writes nothing.

Backout disables new Home Assistant links but retains provider settings and a
minimal disconnect/revoke path until every stored storage token is remotely
revoked and locally erased. `POST /unpair` confirms revocation only after removing
the matching server hash. On transport failure, the build erases local token and
directs the user to revoke that random slot from Home Assistant options.
Mappings, local vaults, and remote objects remain. Reinstalling a compatible build
restores mappings after fresh pairing. Backout never rewrites or deletes
`.kdbx` data and never converts mappings to Google.

## Risks

| Risk | Mitigation |
| --- | --- |
| Home Assistant is mistaken for built-in object storage | Companion requirement and custom API are explicit; core state/media/backup APIs are forbidden |
| Storage credential leaks | 256-bit token scoped to fixed companion routes, hash-only server persistence, platform secure storage, per-slot revocation, no Home Assistant user token |
| Interrupted host write corrupts only remote copy | Same-directory atomic replace, fsync, post-commit verification, live kill probes, local backup/convergence invariants |
| User points mapping at another HA instance | Installation-bound opaque remote ID and fail-closed identity check |
| Companion API and app versions drift | Versioned route, explicit protocol compatibility check, coordinated release/backout |
| Self-hosted TLS is misconfigured | Production HTTPS-only client with normal certificate validation; no bypass |
| Large upload exhausts HA memory/disk | Streaming body, fixed size/object-count limits, free-space/write failure handling, no base64 JSON |
| New resolver becomes plugin framework | Exact two-provider constructor input and lookup only; no dynamic discovery or speculative capabilities |
| HA backups give false version-history confidence | Backup/restore is operational recovery only; provider declares no `versionHistory` capability |
| Backup rollback resurrects revoked credential hash | Restore blocks all views, clears every pairing/token slot before activation, requires fresh pairing; unsupported when restore cannot be detected reliably |
| Home Assistant user token is mistaken for storage authorization | Custom guard rejects HA tokens; only hash-matched storage slots reach body or disk |
| Whole-byte client port exceeds mobile memory | Fixed 64 MiB app/server limit, Android/iOS peak-RSS gate; raise only after streaming or measured headroom |

## Definition of done

- All acceptance criteria pass.
- Companion integration and KeyVault support ship with compatible protocol
  versions and installation instructions.
- Required spec 010 Home Assistant evidence is present and sanitized.
- No optional capability is claimed without separate passing evidence.
- Google sync remains unchanged and fully validated.
- No secret, private endpoint, identity, path, object metadata, or vault bytes
  appear in repository evidence or diagnostics.
- Provider remains disabled on every client/server row marked `fail`; `not-run`
  requires explicit release waiver.

## Deferred questions

- Automatic storage-token rotation may follow after expiry and offline-device
  recovery semantics are specified; initial tokens rotate through explicit
  revoke and fresh one-use pairing.
- Multiple Home Assistant instances require provider-configuration identity in
  application UX and mapping resolution; one instance is enough for first use.
- Conditional writes may be added only after a live stale-write/counter-probe
  proves server enforcement and activates spec 010 capability evidence rules.
- HACS distribution may follow once archive installation and upgrade behavior are
  stable; it is packaging work, not storage correctness.
